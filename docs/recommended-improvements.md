# Recommended Improvements

This is a prioritized list of improvements found from a source-only review of the current ROS 2 workspace. No runtime robot tests were performed for this pass.

## High Priority

### 1. Add a command timeout failsafe in the ESP32 firmware

The ESP32 stops motors when the micro-ROS agent disappears, but the firmware currently keeps the last wheel targets until a new `/diff_cont/cmd_vel_unstamped` message arrives or the agent is lost. If a command publisher dies while the agent remains alive, the robot can continue executing the last command.

Recommendation:
- Track the timestamp of the last received velocity command in `src/esp32_microros/src/main.cpp`.
- If no command arrives within a short timeout, set both PID targets to zero and stop the motors.
- Use a conservative timeout such as 300-500 ms, then tune after driving tests.

This is the most important safety improvement because it belongs at the lowest control layer.

### 2. Add a shutdown stop path to every velocity publisher

Any node that publishes motion commands should send a zero `Twist` before shutdown so normal interrupts and launch shutdowns leave the robot stopped.

Recommendation:
- Add a small `stop_robot()` helper to each motion publisher that can outlive a window or callback.
- Call it before `destroy_node()`.
- Consider publishing the zero command several times over 200-300 ms to give DDS and `twist_mux` time to forward it.

This does not replace the ESP32 failsafe, but it makes the application layer behave more responsibly.

### 3. Remove real secrets from tracked documentation history

The repository documentation includes real-looking WiFi/password examples in project memory/setup docs. Even if those credentials are no longer valid, they should not live in tracked docs.

Recommendation:
- Replace real values with placeholders in docs.
- Rotate any credentials that may have been committed.
- Consider a one-time history cleanup only if this repo will be public or shared broadly.
- Keep `credentials.h` ignored and never print its contents during debugging.

The existing `.gitignore` correctly ignores ESP32 `credentials.h`, but documentation can still leak secrets.

## Medium Priority

### 4. Make generated and local-only files impossible to commit

The workspace root contains `build/`, `install/`, and `log/` generated by colcon. The main repo ignores these paths, but the workspace root is not itself a git repo, so new clones or future workspace-level commits could accidentally capture build output.

Recommendation:
- Add a workspace-level `.gitignore` if the workspace root ever becomes a repo.
- Keep generated colcon output out of source repos.
- Add ignore rules for PlatformIO `.pio/` and all ESP32 test `credentials.h` files in any repo that owns firmware.

### 5. Clean up package metadata

Both packages still have tutorial placeholder metadata such as `TODO: Package description` and `TODO: License declaration`.

Recommendation:
- Update `package.xml` and Python setup metadata with the actual project description, maintainer, and license.
- Keep package metadata consistent with the README badges and repository license.

This is low-risk and helps `rosdep`, package indexing, and future sharing.

### 6. Consolidate active architecture documentation

Some docs still describe the older Arduino/Pi-side sensor stack as if it is active, while newer docs describe ESP32-S3 + micro-ROS as production. This can make debugging harder because the launch files and docs disagree in places.

Recommendation:
- Mark Arduino and `legacy/ros_arduino_bridge` material as legacy reference.
- Make the ESP32 micro-ROS path the primary architecture in README/setup docs.
- Keep one clear "what runs where" table as the source of truth.

### 7. Add launch-level configurability for device paths

Several hardware paths are hardcoded, including `/dev/ttyACM0`, `/dev/rplidar`, and the default map path under `~/mybot_ws/maps`.

Recommendation:
- Expose serial device paths and map path as launch arguments.
- Keep current values as defaults.
- Document common overrides for dev, Pi, and bench-test setups.

This would make recovery from USB enumeration changes less brittle.

### 8. Tune velocity limits consistently across controller layers

Velocity and acceleration limits appear in multiple places: `my_controllers.yaml`, `nav2_params.yaml`, and ESP32 PID behavior. If a velocity smoother is reintroduced later, it should share the same limits. Mismatched limits make tuning harder and can hide where a motion constraint is actually applied.

Recommendation:
- Document the intended physical limits in one place.
- Align `diff_drive_controller`, Nav2 DWB, and firmware assumptions.
- Keep firmware-level limits as the final safety boundary.

## Lower Priority

### 9. Reduce noisy logs in high-rate firmware and tracking paths

The ESP32 firmware logs encoder state at control rate, and the ball detector logs every detected point. That is useful during bring-up but can make real debugging noisy.

Recommendation:
- Add a compile-time or runtime debug flag.
- Keep high-rate logs disabled by default.
- Prefer periodic summary logs for normal operation.

### 10. Add focused tests or smoke checks

The robot stack depends heavily on launch/config correctness. A small set of checks would catch common regressions before field testing.

Recommendation:
- Add a script or documented command set that validates xacro expansion, package discovery, launch argument parsing, and Python importability.
- For firmware, keep PlatformIO test sketches but document the expected pass/fail criteria near each test.

### 11. Clean launch files incrementally

Several launch files still contain tutorial comments, stale commented blocks, or placeholder comments such as "CHANGE ME".

Recommendation:
- Remove stale comments only when touching the relevant launch file for real work.
- Keep comments that explain machine split, safety behavior, or non-obvious ROS remappings.

### 12. Decide whether the vision tracker should stay separate

The tutorial-derived OpenCV tracker is still a separate repo and remains close to upstream example code. If you expect to modify that tracker heavily, vendor or fork it intentionally and document ownership.

Recommendation:
- If it should stay upstream-clean, keep robot-specific behavior in `articubot_one` launch/config and avoid editing the tracker repo directly.
- If it becomes part of the active robot workflow, move it into the main workspace intentionally rather than leaving it as a sidecar repo.

## File Structure Improvements

### 13. Move large generated PlatformIO caches out of the source tree

The ignored PlatformIO cache at `src/articubot_one/src/esp32_microros/.pio` is currently about 968 MB. It is ignored, but it still lives inside the repository working tree and makes search, backup, indexing, and manual inspection heavier.

Recommendation:
- Keep `.pio/` ignored.
- Consider setting PlatformIO build/cache directories outside the repo for this project.
- Periodically remove local `.pio/` directories when not actively flashing firmware.

This is not a correctness issue, but it is the largest avoidable file-structure cost in the workspace.

### 14. Clarify the nested ROS package layout

The setup docs clone this repository into workspace paths such as `~/dev_ws/src/articubot_one` and `~/mybot_ws/src/articubot_one`. Inside that repository, the ROS package also lives under `src/articubot_one`. That works for colcon, but it can be confusing because there are two meaningful roots:

- Repository root: docs, hardware docs, maps, firmware, legacy Arduino bridge.
- ROS package root: launch, config, description, scripts, package manifest.

Recommendation:
- Document explicitly that this repo is a workspace source repository containing multiple subprojects, not a single ROS package directory.
- In setup instructions, consider cloning as `MyBot` or otherwise naming the clone so the nested package path is obvious.
- State that the ROS package path is `<repo>/src/articubot_one`, while colcon should still be run from the workspace root.
- Avoid adding robot runtime files at the repository root unless they are intentionally outside the ROS package.
- If the repo is ever reorganized, consider a clearer split such as `ros/articubot_one`, `firmware/esp32_microros`, `hardware/`, and `docs/`.

Do not restructure this immediately unless there is a real maintenance need, because launch paths, docs, and Pi sync workflows may depend on the current layout.

### 15. Separate firmware from ROS package source

ESP32 firmware currently lives under `src/esp32_microros` inside the main repository's `src/` directory, alongside ROS package and legacy Arduino code. Since `src/` is also the conventional colcon source directory, this mixes ROS packages, firmware projects, and reference code in one namespace.

Recommendation:
- Long term, move firmware to a top-level `firmware/esp32_microros/` directory.
- Keep ROS packages under a clearly named ROS workspace/package directory.
- Update docs and PlatformIO paths in one coordinated change if this move is made.

This would make ownership clearer: ROS packages are built by colcon, firmware is built by PlatformIO.

### 16. Move legacy Arduino bridge under an explicit archive/reference directory

`legacy/ros_arduino_bridge` is documented as legacy reference only and is now outside `src/`, which makes the split clearer.

Recommendation:
- It already lives under `legacy/ros_arduino_bridge/`, so keep it there if it remains reference-only.
- Add a short README at the legacy directory boundary explaining why it is retained.
- Keep active runtime launch/config paths free of legacy assumptions.

This reduces the chance of debugging the wrong motor-control path.

### 17. Group maps with navigation assets or install them deliberately

Saved maps currently live at repository root under `maps/`, while localization defaults to `~/mybot_ws/maps/my_map.yaml`. That is understandable for robot operation, but it means map ownership is split between repo state and machine-local deployment state.

Recommendation:
- Decide whether maps are versioned robot assets or local runtime artifacts.
- If versioned, consider placing them under the ROS package, for example `src/articubot_one/maps/`, and installing them via `CMakeLists.txt`.
- If local-only, keep them out of the repo and document how to restore/deploy them.

The current setup works, but the source/deployment boundary should be explicit.

### 18. Normalize documentation placement and naming

Documentation is split across `README.md`, `docs/`, `Hardware/`, `HARDWARE_MEMORY.md`, `CLAUDE.md`, and several root-level validation/frame files. Some of these are stable project docs, while others appear to be session memory or generated artifacts.

Recommendation:
- Keep stable user-facing docs in `docs/`.
- Keep component-specific hardware docs in `hardware/` or keep `Hardware/` but use one naming convention.
- Move session-oriented memory files under a clearly named internal area, or exclude them from public docs.
- Move generated frame reports such as `frames_*.pdf` and `frames_*.gv` into a diagnostics or artifacts directory if they should stay tracked.

This would make the repository easier to scan for newcomers and future maintenance sessions.

### 19. Add a workspace hygiene note for local tool directories

The workspace root contains local tool directories such as `.agents`, `.codex`, `.claude`, and `.vscode`. They are not part of the robot stack, but they can distract from source layout and may become accidental commit candidates in future repos.

Recommendation:
- Keep local assistant/editor directories ignored in every repo that may contain them.
- Consider a workspace-level `.gitignore` even if `/home/ryan/dev_ws` is not a real repo.
- Avoid placing project instructions only inside local tool directories; keep durable project docs in tracked Markdown files.

### 20. Remove generated Python bytecode from working trees when convenient

Recommendation:
- Leave it ignored.
- Clean it periodically when reviewing or packaging.
- Keep Python caches out of commits.

### 21. Add or correct the root license file

The root README links the MIT license badge and license text to `LICENSE`, but no root `LICENSE` file currently exists.

Recommendation:
- Add a root `LICENSE` file if MIT is the intended project license.
- If the license is stored somewhere else, update the README badge and license section to link to that actual file.
- Keep package metadata license declarations consistent with the root license.

This fixes a dead local link and removes ambiguity for anyone reusing or sharing the code.

### 22. Normalize asset filenames used by documentation links

At least one hardware doc links to an image with a URL-encoded filename, `../DC12V%20Encoder%20Gear%20Motor.png`, while the actual file contains spaces. GitHub usually renders this, but local link checkers and scripts can treat encoded paths inconsistently.

Recommendation:
- Prefer lowercase, hyphenated asset filenames such as `dc12v-encoder-gear-motor.png`.
- Update Markdown references when filenames are normalized.
- If filenames with spaces are kept, validate links with the same renderer/tooling used for project QA.

This is a minor hygiene issue, but it reduces false-positive broken-link reports.

## Suggested Order

1. ESP32 command timeout failsafe.
2. `follow_ball` shutdown stop behavior.
3. Replace/rotate any committed secrets.
4. Align active architecture docs around ESP32 micro-ROS.
5. Move or periodically clean large generated PlatformIO caches.
6. Add or correct the root `LICENSE` file.
7. Clean package metadata and launch configurability.
8. Clarify the long-term source layout for ROS packages, firmware, legacy code, and maps.
9. Normalize documentation asset filenames when touching those docs.
